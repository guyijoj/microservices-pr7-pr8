# Практическая работа 7 — Бочаров

Учебная система доставки еды из четырёх самостоятельных FastAPI-приложений.
Каждое работает в отдельном контейнере со своей PostgreSQL-базой. RabbitMQ
передаёт события по схеме из практики 5. Полный сценарий запускает `demo.py`.

## Быстрый запуск на Mac

1. Запусти Docker Desktop или другой установленный Docker engine.
2. Выполни в терминале:

```bash
cd /Users/guyijoj/Documents/uni/files/МСА/prak7
docker compose up --build -d --wait
python3 demo.py
```

Первая сборка скачивает образы и библиотеки, поэтому может занять несколько минут.
`demo.py` требует только стандартную библиотеку Python 3.9 или новее.

При повторном показе преподавателю достаточно `docker compose up -d --wait`
и `python3 demo.py`. Каждый запуск демо создаёт новый заказ с новым ключом.

| Приложение | Swagger для ручной проверки |
|---|---|
| Заказ | http://localhost:8001/docs |
| Платёж | http://localhost:8002/docs |
| Доставка | http://localhost:8003/docs |
| Уведомления | http://localhost:8004/docs |
| RabbitMQ | http://localhost:15673 — student / student |

Брокер этой практики использует порты 5673 и 15673, поэтому может работать рядом
с RabbitMQ из практики 5 на стандартных портах. Очереди здесь durable, поскольку
это событийная система из задания 2 практики 5. Индивидуальный вариант 3 с fanout
и случайной задержкой относится к отдельным producer/consumer из `../prak5`.

## Что реализовано по требованиям методички

| Требование | Реализация |
|---|---|
| Все ранее описанные сервисы | orders, payments, deliveries, notifications |
| От 2 до 5 эндпоинтов на сервис | 4, 3, 4, 2 соответственно, без служебных Swagger-маршрутов |
| HTTP-вызов другого сервиса | POST /api/payments вызывает GET /api/orders/{id} |
| Работа с БД | Все четыре сервиса, отдельные базы в одном сервере PostgreSQL |
| Отдельные Docker-контейнеры | Четыре образа с отдельной точкой входа, плюс PostgreSQL и RabbitMQ |
| Общий запуск | compose.yaml |

В практике 6 у Заказа было 7 методов. Для ограничения в 5 эндпоинтов команды
собраны в `POST /api/orders/{id}/commands/{action}`. Значения `action` —
`confirm`, `cancel`, `startPreparation`, `markPrepared`. Бизнес-действия сохранены.
У списков реализованы `order_id`, `status`, `offset`, `count` и ограничение доступа.
Фильтры `user_id`, `restaurant_id`, `courier_id` из расширенного проекта API здесь
заменены автоматической областью доступа текущего участника.

| Файл | Назначение |

Общий исходный код используется как учебная библиотека. Контейнеры имеют
отдельные процессы, API и БД. Они обмениваются данными через HTTP и RabbitMQ.

## Доступ и учебные ограничения

В Swagger передавай параметр `authorization` целиком с префиксом `Bearer `.

| Значение заголовка Authorization | Роль |
|---|---|
| Bearer customer-bocharov | Клиент user-bocharov |
| Bearer restaurant-demo | Ресторан restaurant-1 |
| Bearer courier-demo | Курьер courier-1 |
| Bearer service-demo | Внутренний сервис |

Это фиксированные демонстрационные токены, без сервера OAuth и без granular scopes.
Провайдер оплаты учебный: `:check` подтверждает оплату. Демокаталог содержит
`restaurant-1`, блюда `dish-1` за 55000 копеек и `dish-2` за 15000 копеек.
Курьер назначается автоматически из одного доступного `courier-1`.
Push-уведомления сохраняются в БД со статусом `sent`, внешний push-провайдер не вызывается.
HTTP используется локально без TLS. Для этой учебной демонстрации этих адаптеров достаточно.

## HTTP API

| Сервис | Метод и путь | Роль |
|---|---|---|
| Заказ | POST /api/orders | customer |
| Заказ | GET /api/orders | По доступу |
| Заказ | GET /api/orders/{id} | По доступу |
| Заказ | POST /api/orders/{id}/commands/{action} | restaurant |
| Платёж | POST /api/payments | customer, service |
| Платёж | GET /api/payments/{id} | Владелец, service |
| Платёж | POST /api/payments/{id}:check | service |
| Доставка | GET /api/deliveries | По доступу |
| Доставка | GET /api/deliveries/{id} | По доступу |
| Доставка | POST /api/deliveries/{id}:accept | Назначенный courier |
| Доставка | POST /api/deliveries/{id}:complete | Назначенный courier |
| Уведомления | GET /api/notifications | Владелец, service |
| Уведомления | GET /api/notifications/{id} | Владелец, service |

При создании заказа и платежа нужен `Idempotency-Key` от 1 до 128 символов.
Ключ действует 24 часа в пределах участника и метода создания. Совпадающее тело
возвращает первоначальный объект и код 201, другое тело — 409. Проверка оплаты
и повторы текущего перехода не создают новых событий. Недопустимые переходы — 409.

## События

Обменник `food.events`, тип `topic`. Очереди `bocharov.orders`,
`bocharov.deliveries`, `bocharov.notifications`.

| Событие | Отправитель → Получатель | Действие |
|---|---|---|
| payment.confirmed | Платёж → Заказ | awaiting_payment → paid |
| order.confirmed | Заказ → Уведомления | Сообщить о подтверждении |
| order.cancelled | Заказ → Уведомления | Сообщить об отмене с причиной |
| order.prepared | Заказ → Доставка | Создать доставку, назначить курьера |
| delivery.completed | Доставка → Уведомления | Сообщить о доставке |

В событии есть `event_id`, `event_type`, `schema_version=1`, `occurred_at`,
`correlation_id` и `data`. Идентификаторы — строки, деньги — копейки, валюта — RUB.
Outbox сохраняет событие в одной транзакции с изменением объекта. Publisher
повторяет отправку при сбое. Inbox защищает обработчик от повторного `event_id`.
Успешная обработка подтверждается ack. Некорректное сообщение отклоняется и
пишется в лог, временная ошибка БД приводит к повторной доставке.

## Как показать преподавателю

1. Выполни `docker compose ps` — должно быть шесть работающих контейнеров.
2. Открой Swagger четырёх сервисов и RabbitMQ.
3. Выполни `python3 demo.py`. Сценарий создаёт заказ, платёж, проверяет оплату,
   подтверждает заказ рестораном, начинает и завершает приготовление, принимает
   и завершает доставку курьером. Асинхронные шаги ожидаются с ограничением времени.
4. В GET-методах найди заказ, платёж, доставку и два уведомления по выведенным ID.
5. Повтори текущую команду с теми же данными — результат 200. Попробуй завершить
   доставку до принятия — 409.
6. Перезапусти контейнеры `docker compose restart` и проверь сохранённый объект.

Полезные скриншоты для отчёта: список контейнеров, вывод demo.py, Swagger с
созданным объектом и списком уведомлений, очереди RabbitMQ.

## Проверки

Локальные тесты можно запускать отдельно от Docker:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest -q
```

Пять тестов проверяют HTTP-контроллеры с SQLite, бизнес-сценарий, дублирование
событий, идемпотентность, права, отмену, персистентность и ошибку HTTP-зависимости.
В тестах событие из outbox передаётся обработчику напрямую, HTTP-зависимость
подменяется транспортом. Это не проверка настоящих RabbitMQ и PostgreSQL.
Полная проверка транспорта — `demo.py` после запуска Compose.

При подготовке проекта выполнено: `5 passed`, `docker compose config --quiet`.
Полный контейнерный запуск ещё не проверен: Docker engine в среде подготовки недоступен.

## Остановка и диагностика

```bash
docker compose ps
docker compose logs --tail=50
docker compose logs -f orders payments deliveries notifications
docker compose stop
```

`stop` сохраняет базы и брокер в томах. Для повторного запуска — `docker compose up -d --wait`.
Если Docker сообщает `Cannot connect to the Docker daemon`, запусти Docker engine.
Если порт 8001–8004 или 15673 занят, освободи его либо поменяй только левую часть
соответствующего порта в Compose и адреса в demo.py.
