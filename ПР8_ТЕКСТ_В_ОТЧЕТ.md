# Практическая работа №8. Тестирование микросервисов

## Цель работы

Изучить виды pre-deployment тестирования и получить практические навыки разработки автоматизированных тестов микросервисной системы.

## 8.1. Выбор видов тестирования

В соответствии с методическими указаниями выбраны два вида тестирования: модульное (unit) и компонентное. Объект тестирования — система доставки еды из практической работы №7 (микросервисы «Заказ», «Платёж», «Доставка», «Уведомления»). Основное внимание уделено моделям данных и бизнес-логике сервиса «Заказ», а также межсервисному сценарию оформления заказа, подтверждения оплаты и доставки.

Unit-тесты проверяют отдельные модели и функции без запуска сети, брокера сообщений или PostgreSQL. Компонентные тесты проверяют сервис снаружи через его HTTP-интерфейс при замене внешних зависимостей тестовыми адаптерами. В дополнение подготовлен отдельный набор сквозных проверок для запущенных Docker-контейнеров, требующий реальной среды.

## 8.2. Структура набора тестов

Тесты на языке Python написаны с использованием pytest. Файлы размещены в каталогах `tests/unit`, `tests/component` и `tests/e2e`. Для параметризованных проверок используются декораторы `@pytest.mark.parametrize`; общие подготовительные данные и временные хранилища создаются с помощью pytest-фикстур. Включён файл конфигурации `pytest.ini`.

| Файл | Вид | Назначение |
|---|---|---|
| `tests/unit/test_models.py` | Unit | Pydantic-модели, обязательные поля, типы и граничные значения |
| `tests/unit/test_orders.py` | Unit | Расчёт стоимости, создание заказов, права, переходы статусов и идемпотентность |
| `tests/unit/test_payment_delivery_events.py` | Unit | Платежи, переходы доставки, обработка асинхронных событий и защита от повторов |
| `tests/component/test_orders_http.py` | Компонентное | HTTP API заказов, авторизация, ошибки, параметры списков |
| `tests/component/test_workflow_http.py` | Компонентное | HTTP платёжного сервиса, недоступность зависимости, полный бизнес-сценарий |
| `tests/e2e/test_live_docker.py` | Дополнительно | Проверка реальных контейнеров и цепочки через RabbitMQ |

## 8.3. Unit-тестирование моделей

Проверена модель `OrderItem`: поле `quantity` принимает целые числа от 1 до 99 и отклоняет числа вне диапазона, строки, дробные числа и логическое значение. Для `Address` проверены ограничения широты от −90 до 90, долготы от −180 до 180, длины адреса от 1 до 500 символов. Модель `CreateOrder` проверена на обязательность непустого списка позиций, идентификатора ресторана и адреса доставки. Для `Event` проверены допустимые типы событий и версия схемы.

## 8.4. Unit-тестирование бизнес-логики

Для изоляции зависимостей реализован класс `FakeTx`, имитирующий интерфейс `UnitOfWork` приложения. Вместо запросов к БД информация хранится в словаре в памяти. Такой подход позволяет проверить `create_order`, `idempotent`, `order_command`, `create_payment`, `check_payment`, `delivery_command` и `handle_event` без запуска базы данных и брокера.

Проверены бизнес-правила: сервер рассчитывает сумму по учебному каталогу (два блюда `dish-1` по 55000 копеек и одно `dish-2` за 15000 копеек — всего 125000 копеек), неподтверждённая оплата не разрешает подтвердить заказ, повторы команд не создают повторных событий. Также проверены ограничения прав пользователей, обязательность причины отмены, запрет недопустимых переходов состояния и обработка повторного `event_id`.

## 8.5. Компонентное тестирование

Проверки выполняются через `fastapi.testclient.TestClient`, посылающий реальные HTTP-запросы в ASGI-приложения. Каждый тест работает с отдельными SQLite-файлами во временном каталоге, а обращения сервиса «Платёж» к сервису «Заказ» перехватываются `httpx.MockTransport`. Поэтому внешний HTTP-сервер, PostgreSQL и RabbitMQ для этих тестов не требуются. Асинхронные события передаются в обработчик `handle_event` напрямую, что позволяет проверить предметную логику без сетевого брокера.

Проверяются HTTP-коды `201`, `401`, `403`, `404`, `409`, `422` и `503`, заголовок `Location`, идентификаторы заказов, расчёт суммы, фильтры и пагинация. Реализована проверка полного сценария: создать заказ, создать платёж, подтвердить оплату, подтвердить и приготовить заказ, создать доставку, принять и завершить доставку, получить два уведомления.

Разработан набор автоматизированных тестов микросервисной системы доставки еды. Подготовлен дополнительный набор тестов, позволяющий проверить реальные контейнеры и асинхронное взаимодействие через RabbitMQ при наличии запущенной системы.
